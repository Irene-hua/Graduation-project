# 本地轻量RAG系统方法设计与优化说明

## 1 系统设计

### 1.1 设计目标与总体思路

为提高本地轻量级检索增强生成（RAG）系统在复杂问答场景下的答案准确率、证据可解释性与工程稳定性，本文在原有“检索—生成”框架基础上，引入标准的两阶段检索架构，即 **Retrieve → Rerank → Context → Generate**。该设计的核心目标在于：一方面通过扩大初始候选集合提高召回能力，尽可能覆盖与问题相关的潜在证据；另一方面通过精排模块提升候选排序精度，使真正能够支撑答案生成的高质量证据优先进入上下文，从而降低噪声干扰和生成幻觉风险。

从系统实现角度看，本文保持原有模块化设计，不删除任何既有模块，也不改变 `RuleEngine` 的 fallback 机制。系统仍然由检索、精排、上下文构建、生成与规则兜底等独立模块组成，各模块职责清晰、接口明确，便于后续扩展与论文说明。其中，`rag_system.py` 作为总控编排器，负责将检索结果、精排结果、上下文预算与 LLM 生成统一组织起来；`HybridReranker` 负责可选的双模式精排；`LocalReranker` 负责在轻量级场景下提供确定性的本地排序能力；`ContextBuilder` 负责控制上下文长度并过滤低质量证据；`TemporalComparisonRule` 则仅作为窄范围 fallback，在主流程无法给出有效答案时提供补充支持。

### 1.2 检索阶段：召回优先的候选扩展

在检索阶段，系统首先由 `Retriever` 基于嵌入模型将用户查询向量化，并从向量数据库中召回相关候选片段。为了提高召回率，本文不再仅使用固定 `top_k` 作为检索规模，而是采用更大的候选规模：

\[
retrieve\_k = \max(4 \times top\_k, 20)
\]

这样做的原因在于，初始检索更强调 Recall，即尽可能找全相关证据。对于时间问答、邮件证据定位、先后顺序判断等任务，相关证据常常分散在多个相似片段中，如果检索候选过少，容易出现漏召回，从而影响后续回答的完整性。因此，扩大候选集是标准两阶段检索的第一步。

### 1.3 精排阶段：以 CrossEncoder 为优先的本地 rerank

在候选扩展之后，系统将候选块输入本地精排模块 `HybridReranker`。该模块采用“双模式”设计：优先使用本地 `CrossEncoder` 模型 `cross-encoder/ms-marco-MiniLM-L-6-v2` 对“查询—候选块”进行交叉编码评分；若模型加载失败或运行异常，则自动回退到轻量级的 `LocalReranker`。这种设计在保证本地离线运行的前提下，尽可能提升排序精度。

交叉编码器与传统向量检索模型的区别在于：传统向量检索通常采用双塔结构，分别编码查询和文本，再通过向量相似度进行匹配，适合大规模召回；而 CrossEncoder 会将查询与候选文本拼接后共同编码，能够直接学习二者之间的交互关系，更适合精排阶段。因此，本文将 CrossEncoder 作为精排优先方案，以提升“证据是否真正回答了问题”的判别能力。

若 CrossEncoder 不可用，系统会自动回退到 `LocalReranker`。该模块基于词项重叠、时间信号和元数据先验进行打分，虽然模型能力弱于 CrossEncoder，但实现简单、执行稳定、可解释性强，适合作为工程和论文场景中的兜底方案。该设计确保系统在任何本地环境下都可运行，不依赖云 API，也不破坏原有主流程。

#### 精排分数定义

设查询为 \(q\)，初始候选集合为 \(C = \{c_1, c_2, \dots, c_n\}\)，则精排模块为每个候选块计算一个相关性分数 \(s(q, c_i)\)，并按分数降序排序：

\[
\hat{C} = \text{Sort}(C, s(q, c_i))
\]

其中，CrossEncoder 模式下的 \(s(q,c_i)\) 由模型直接输出；LocalReranker 模式下的 \(s(q,c_i)\) 则由词项重叠、时间戳匹配与元数据先验共同构成。

### 1.4 上下文构建：预算控制与高质量证据保留

在上下文构建阶段，系统使用 `ContextBuilder` 对 rerank 后的候选片段进行筛选与拼接。该模块不仅控制最大上下文长度，还会优先保留 rerank 分数较高的片段，避免低质量候选占用 prompt 预算并干扰生成质量。具体而言，设最终保留的上下文片段为 \(c'_1, c'_2, \dots, c'_m\)，则上下文构建可表示为：

\[
X = \text{Concat}(c'_1, c'_2, \dots, c'_m)
\]

并满足字符数或 token 数上限约束。该设计可以防止提示词过长导致的上下文截断，同时确保大语言模型接收到的主要是高置信度证据，从而提高答案稳定性。

### 1.5 生成阶段：答案有效性判断与 fallback 规则

在生成阶段，系统调用本地大语言模型基于上下文 \(X\) 生成最终答案 \(a\)：

\[
a = \text{LLM}(q, X)
\]

为了提升系统鲁棒性，本文引入了答案有效性判断函数 `is_valid_answer()`。该函数会过滤掉诸如 “Not found”、“I don't know”、“cannot find”、“no information”等弱回答或无效回答，避免将模型的兜底式输出误判为有效结果。若主路径生成结果无效，则系统继续调用 `RuleEngine` 作为最后的窄范围 fallback。当前系统仅保留泛化能力较强的 `TemporalComparisonRule`，用于处理时间先后、时间差等明确时间表达任务，从而避免规则系统过度硬编码。

需要强调的是，`RuleEngine` 并不参与主流程，而仅在主路径无法生成有效答案时提供补救支持。这样的设计既保留了系统在特定任务上的确定性补充能力，也避免了规则逻辑干扰主 RAG 流程。

### 1.6 结果解释字段设计

为增强系统的可解释性与论文展示效果，本文在返回结果中加入了以下解释性字段：

- `retrieve_k`：实际扩大后的召回候选规模；
- `rerank_enabled`：是否启用了 rerank；
- `rerank_before_top1` / `rerank_after_top1`：rerank 前后排名第一的候选块；
- `rerank_top_scores`：精排后前三个候选的分数；
- `context_length`：最终拼接上下文长度。

这些字段可以帮助分析：召回扩展是否足够、精排是否有效、上下文是否过长，以及最终答案是否有可靠证据支撑。对于毕业论文而言，这些字段不仅支持实验结果分析，也增强了系统可解释性。

### 1.7 系统优势总结

综上，本文采用的两阶段检索式 RAG 方案在不破坏原有系统结构的前提下，显著提升了本地轻量级 RAG 系统在复杂问答任务中的准确率、稳定性与可解释性。其主要优势包括：

1. **召回与精度兼顾**：通过扩大候选集提升 Recall，通过 rerank 提升 Precision；
2. **完全本地化**：CrossEncoder 与 LocalReranker 均可本地运行，无需云 API；
3. **模块化清晰**：检索、精排、上下文构建、生成与 fallback 各司其职；
4. **可解释性强**：返回多种解释性字段，便于论文分析与答辩展示；
5. **可扩展性好**：未来可直接替换更强的本地 rerank 模型，而不影响整体架构。

## 2 实验设计

### 2.1 实验目标

本实验的主要目标是验证两阶段检索架构是否能够在不增加云端依赖的前提下，提升本地 RAG 系统的答案准确率与证据排序质量。具体关注以下几个问题：

1. 扩大召回候选集后，是否能够提高相关证据的覆盖率；
2. 引入 rerank 后，是否能够将真正有效的证据排到前列；
3. 上下文长度控制是否有助于减少噪声并提升生成稳定性；
4. 规则 fallback 是否仅在主路径无效时触发，且不会干扰主流程。

### 2.2 对比设置

实验中可以采用以下对比方式：

- **Baseline A**：仅使用向量相似度检索，不进行 rerank；
- **Baseline B**：使用 `LocalReranker` 进行轻量精排；
- **Ours**：使用 `HybridReranker`，优先 CrossEncoder，失败后回退到 `LocalReranker`。

通过对比不同设置下的答案质量、上下文质量与生成稳定性，可以验证两阶段检索的有效性。

### 2.3 评价指标

本文建议从以下几个维度评价系统：

- **答案准确性**：人工判断或基于标准答案计算 Exact Match / F1；
- **上下文命中率**：rerank 后高质量证据是否更靠前；
- **可解释性指标**：rerank 前后 top1 是否变化，精排分数是否合理；
- **效率指标**：检索时间、生成时间、总耗时；
- **鲁棒性指标**：当 CrossEncoder 不可用时，系统是否能自动回退并继续运行。

### 2.4 实验数据与场景

实验数据可采用包含时间问答、邮件问答与事实定位任务的数据集。此类任务通常对证据位置和时间信息较敏感，非常适合验证 rerank 在“精确证据排序”上的收益。对于每个查询，系统记录 `retrieve_k`、`rerank_top_scores`、`context_length` 等解释性字段，并与答案结果一并保存，以便后续分析。

### 2.5 实验结论预期

预期结果表明：当系统引入两阶段检索之后，候选证据的排序质量会明显提升，最终答案的稳定性与准确率也会相应提高。尤其在复杂问答和时间推理任务中，HybridReranker 能够有效减少“语义相近但证据不精确”的片段进入上下文，从而提高最终生成答案的可靠性。

## 3 算法流程图说明

### 3.1 流程概述

本系统的算法流程可概括为：

1. 输入用户查询 \(q\)；
2. 使用嵌入模型将查询向量化；
3. 从向量数据库召回扩大候选集；
4. 使用 `HybridReranker` 对候选集进行重排序；
5. 使用 `ContextBuilder` 构建受长度约束的上下文；
6. 调用本地 LLM 生成答案；
7. 若答案无效，则由 `RuleEngine` 做 fallback。

### 3.2 图注建议

可在论文中将该流程图标注为：

**图 X 本地轻量 RAG 系统的两阶段检索与生成流程**

图中建议明确标出以下模块：

- `Retriever`：负责召回候选证据；
- `HybridReranker`：负责候选重排序；
- `ContextBuilder`：负责上下文预算控制与拼接；
- `LLMCaller`：负责最终答案生成；
- `RuleEngine`：负责主路径失败后的补充判断。

### 3.3 图示说明文字（可直接放图下）

系统首先对用户查询进行向量化，并从 Qdrant 中召回候选片段。随后，HybridReranker 对候选片段进行二次排序，优先保留与问题最相关、证据最充分的片段。ContextBuilder 再将高质量片段拼接成受长度约束的上下文，交由本地大语言模型生成答案。若模型输出无效，则系统调用 RuleEngine 进行窄范围 fallback。该流程在兼顾召回率与精度的同时，保证了系统完全本地化、可解释且可扩展。

## 4 小结

本文围绕本地轻量 RAG 系统的准确率与可解释性问题，构建了标准的两阶段检索与生成方案，并设计了 HybridReranker、ContextBuilder 与答案有效性判断等关键模块。通过扩大召回、精排重排序与上下文预算控制，系统在不破坏原有架构与 fallback 逻辑的前提下，提升了复杂问答任务中的答案质量、稳定性与论文可展示性。该设计为后续实验对比、消融分析与答辩展示提供了完整且清晰的方法基础
